<a id="title-and-document-purpose"></a>
## 1. Title and document purpose

`ork_planner` — пилотный подпроект для внедрения активной рабочей модели:

```text
Planner -> Orc
```

Цель этого файла — дать Planner-у большой, подробный и операционный master document, который можно локально проверить, исправить и принять как основу для дальнейшего движения. Это не короткая заметка и не вдохновляющий манифест. Это рабочая карта: что должно быть сделано, почему именно так, где Planner обязан остановиться, когда появляется Orc, какие документы появятся позже, какие ворота acceptance должны закрыться, и почему repo-level alignment начинается только после локального доказательства.

Главная практическая задача документа: не просто описать желаемую систему, а провести `ork_planner` от planner-owned first draft до первого реального Orc run так, чтобы не произошло смешение ролей. В прошлом риск был в том, что Planner начинал вести себя как смесь Planner + Orc: создавал или планировал live operational layer слишком рано, переходил от стратегии к выполнению, заводил документы статуса и журнала до утверждённого execution phase. Этот документ должен сделать границу жёсткой и понятной.

Документ отвечает на вопросы:

- зачем существует подпроект `ork_planner`;
- почему он является pilot subproject, а не meta-control center всего репозитория;
- какие источники имеют приоритет;
- что принадлежит Planner-у;
- что будет принадлежать Orc после явного запуска;
- какие артефакты можно создать сейчас, а какие нельзя;
- как V3-first-draft отличается от `/v3 import-entry`;
- как должен выглядеть первый Orc navigation pass;
- почему после nav pass не начинается сразу execution, а сначала появляются battle plans;
- что такое три hard phases пилота;
- как отделяются session и journal;
- что считается локальным доказательством модели;
- когда допустима repo-level alignment wave;
- какие решения ещё открыты.

Ключевое правило чтения:

```text
Planner output complete != Orc started.
```

Даже если этот документ становится хорошим и полным, это ещё не execution. Пока человек и Planner не приняли его локально, он остаётся предложением. Даже после принятия этого файла Orc не считается запущенным автоматически. Orc появляется только после явного перехода к execution phase и должен начать с ограниченного, безопасного nav pass.

<a id="mission-of-ork-planner"></a>
## 3. Mission of ork_planner

Миссия `ork_planner` — безопасно внедрить и доказать систему `Planner -> Orc` на одном ограниченном подпроекте, прежде чем выравнивать весь repo-level workflow layer.

Это важно по трём причинам.

Первая причина: система меняет не один файл, а сам способ работы. Нужно разделить planning и execution так, чтобы Planner не становился исполнителем, а Orc не переписывал стратегию без разрешения. Если это не закрепить на пилоте, затем ошибка размножится в правилах, navigation, session workflow, external route и Kilo handoff-ах.

Вторая причина: пользователь не программист и хочет управляемый процесс. Ему важно понимать, где план, где живое выполнение, где журнал, где статус, где решение, где внешний черновик, где локально подтверждённый факт. Документация должна работать как понятная память процесса, а не как набор файлов, которые понятны только агенту.

Третья причина: прежние block-orchestration идеи должны остаться историей, а не вернуться под новыми именами. В активной модели есть один Planner и один Orc для подпроекта. V1/V2/V3/Kilo являются инструментами, а не постоянными параллельными участниками управления.

Практическая миссия подпроекта:

1. Создать и принять сильный `ork_planner_plan_full.md`.
2. Использовать его как основу для первого ограниченного Orc nav pass.
3. После nav pass создать battle plans отдельным шагом.
4. Получить human approval на battle plans.
5. Выполнить первый docs execution slice.
6. Доказать, что новая модель работает локально.
7. Только после этого делать repo-level alignment wave.

`ork_planner` не должен становиться вечным штабом. Он должен быть испытательным стендом: достаточно большим, чтобы проверить реальные проблемы, и достаточно ограниченным, чтобы не сломать весь workflow.

<a id="non-goals-and-forbidden-drifts"></a>
## 4. Non-goals and forbidden drifts

Этот раздел нужен как защита от самого вероятного drift-а. Если будущий агент читает только заголовки и начинает «делать полезное», он может случайно превратить planning artifact в live execution layer. Это запрещено.

### 4.1. Не-цели текущего first draft

Этот документ не должен:

- запускать Orc;
- создавать live `journal`;
- создавать live `status`;
- создавать live `decisions`;
- создавать `plan_active_N`;
- создавать `ork_planner_navigation.md`;
- создавать `ork_planner_plan_navigation.md`;
- создавать `ork_planner_plan_index.md`;
- создавать `ork_planner_readme.md`;
- обновлять `.ai/repo_navigation.md`;
- обновлять `.ai/project_state.md`;
- менять `.ai/rules/`;
- менять `AGENTS.md`;
- делать import через `/v3`;
- делать journaling;
- утверждать, что пакет уже применён к repository workspace.

Текущая задача — один проектный файл в ZIP artifact package. Всё остальное — либо служебная обёртка пакета, либо будущая работа после review.

### 4.2. Запрещённые drift-и

#### Drift A — Planner начинает выполнять

Симптом: Planner не только описывает план, но и создаёт operational docs, ведёт journal, обновляет status, фиксирует execution decisions, формирует live active plan.

Правильная реакция: остановиться. Planner может описать, какие документы появятся позже, но не должен вести их как живой слой без explicit Orc phase.

#### Drift B — Orc появляется без approval

Симптом: после создания `plan_full` агент пишет так, будто Orc уже прочитал план, сделал nav pass или начал execution.

Правильная реакция: заменить claims на future-tense. Формула:

```text
Этот документ предлагает первый шаг для будущего Orc. Orc ещё не запускался.
```

#### Drift C — историческая схема возвращается как active route

Симптом: в документации снова появляется active route через старые многоступенчатые блоки, постоянных младших оркестраторов или отдельный управляющий слой, который подменяет `Planner -> Orc`.

Правильная реакция: оставить такие упоминания только как historical/legacy warning. Активный маршрут один:

```text
Planner -> Orc
```

#### Drift D — V3-first-draft путается с `/v3 import-entry`

Симптом: пакет external-first-draft автоматически считается пакетом для немедленного импорта через `/v3`.

Правильная реакция: зафиксировать, что это artifact generation only. `/v3 import-entry` начинается только когда человек явно приносит package source и просит пройти import route.

#### Drift E — repo-level alignment начинается до local proof

Симптом: до проверки локального пилота агент начинает переписывать repo-level правила, навигацию и project state.

Правильная реакция: заблокировать. Сначала local proof, затем repo-level alignment wave.

## 5. Source basis and source authority order

Этот first draft основан на commit-pinned источниках из запроса. Источники должны читаться не как равные по силе. Для `ork_planner` нужен порядок authority, чтобы исторический scaffold или общая идея не перебили свежие planner-owned решения.

### 5.1. Authority order

1. **Текущий V3 request**  
   Самый высокий приоритет для этого артефакта: создать ZIP package, внутри один project file `.ai/subprojects/ork_planner/ork_planner_plan_full.md`, документ на русском языке, без запуска import, без Kilo Notebook V3, без journaling, без записи в repo.

2. **Planner-owned decisions для `ork_planner`**  
   `ork_planner_plan_decisions.md` имеет высокий приоритет для решений именно этого подпроекта. Он фиксирует, что новый старт planner-first, что `plan_full` должен довести до первого Orc run, что первый Orc шаг — узкий nav pass, что battle plans отделены от nav pass, и что acceptance пилота не равен созданию файлов.

3. **Planner request ideas для `ork_planner`**  
   `ork_planner_planner_request_ideas.md` фиксирует идеи будущих route-ов. Для этой задачи особенно важно, что `First V3 draft package for ork_planner_plan_full.md` уже promoted как `V3-Ревью`, но не как `/v3 import-entry`.

4. **Repo-level Planner role contract**  
   `codex_role_planner.md` определяет Planner как planning role: понять задачу, прочитать контекст, выявить constraints, определить acceptance criteria и подготовить достаточно ясный план для Orc. Planner не является default execution role.

5. **Repo-level Orc role contract**  
   `codex_role_orc.md` определяет Orc как execution orchestration role: Orc выполняет принятый Planner plan, выбирает route шаг за шагом, ведёт evidence, journal/status/decisions и возвращается к Planner, если план недостаточен.

6. **Codex orchestrator contract**  
   `codex_orchestrator.md` задаёт активную repo-level модель, shortcut boundaries, разделение `/v1`, `/r1`, `/v3`, Kilo, External Web Chat, а также фиксирует, что закрытая block-orchestration система является legacy/history only, а активный route — `Planner -> Orc`.

7. **Subagent tool distinctions**  
   `subagent_tools.md` полезен для выбора tool label: `V1-Синтез`, `V3-Ревью`, `Kilo`, `Субагент-микро`. Для текущей задачи выбран `V3-Ревью` как strong external draft/artifact first, но это не `/v3 import-entry`.

8. **Source idea document**  
   `subproject_single_execution_chat_documentation_system_v2.md` описывает общую идею: один planning chat, один execution chat, документация как внешняя память, V1/V2/V3/Kilo как инструменты. Он важен как концептуальная база.

9. **Historical scaffold reference-only example**  
   Старый scaffold полезен только как предупреждение и reference-only пример. Его нельзя копировать как template, потому что он предлагал раньше создать полный стартовый набор документов, а текущая задача требует один файл first draft и более строгую Planner/Orc границу.

### 5.2. Что делать при конфликте источников

Если source idea говорит «обычно подпроект содержит много файлов», а текущий request говорит «создать только один project file», побеждает текущий request.

Если historical scaffold показывает `readme`, `navigation`, `journal`, `status`, но текущая задача запрещает создавать их сейчас, побеждает текущий request и planner-owned decisions.

Если общий workflow говорит, что Orc ведёт journal/status/decisions, это не даёт Planner-у права создать их заранее. Это означает: когда Orc будет явно запущен, он станет владельцем live operational layer.

Если где-то встречается старая terminology из закрытой block-orchestration системы, она не возвращается как active route. В документе допустимо упомянуть её только как forbidden drift или historical note.

<a id="planner-role-boundaries"></a>
## 6. Planner role boundaries

Planner — это роль планирования. В контексте `ork_planner` Planner отвечает за качество полного плана и за удержание стратегии до момента передачи Orc-у.

Planner должен:

- понять задачу в практических терминах;
- определить intended outcome;
- выделить non-goals;
- перечислить allowed и forbidden paths;
- прочитать и честно учитывать источники;
- разделить confirmed facts и assumptions;
- определить риски, blockers, unresolved decisions;
- определить порядок работы;
- определить acceptance gates;
- определить human checkpoints;
- объяснить, где первый Orc должен начать;
- описать, когда Orc обязан остановиться;
- оставить достаточно деталей, чтобы Orc не изобретал стратегию заново.

Planner не должен:

- выполнять substantive repo work;
- делать live execution changes;
- вести operational journal;
- утверждать status выполнения;
- создавать active execution plan как будто Orc уже работает;
- выбирать конкретный Kilo mode вместо будущего Orc, если это намеренно оставлено на Orc;
- делать claims о локальном repo state без локальной проверки;
- превращать external artifact в accepted decision;
- закрывать gates без evidence.

### 6.1. Правильная формула остановки Planner-а

В конце planner-stage правильная формула такая:

```text
Planner output complete: plan_full готов для локального review. Orc ещё не запущен.
```

Эта формула важна, потому что она не смешивает две вещи:

- наличие хорошего плана;
- начало исполнения.

### 6.2. Что Planner может описывать, но не создавать сейчас

Planner может подробно описать будущие документы:

- `ork_planner_readme.md`;
- `ork_planner_plan_navigation.md`;
- `ork_planner_plan_index.md`;
- `ork_planner_navigation.md`;
- `ork_planner_plan_active_N.md`;
- `ork_planner_journal.md`;
- `ork_planner_status.md`;
- `ork_planner_decisions.md`.

Но в текущем V3-first-draft package Planner не создаёт эти project files. Их появление относится к будущим Orc-owned steps.

## 7. Planner-owned vs Orc-owned artifacts

Разделение artifact ownership — основной механизм защиты от role drift.

### 7.1. Planner-owned artifacts

Planner-owned layer — это документы и заметки, которые помогают подготовить и удержать стратегию. Для `ork_planner` сюда относятся:

- `ork_planner_plan_full.md` — главный большой план;
- `ork_planner_plan_decisions.md` — planner-owned decision log planning-stage;
- `ork_planner_planner_request_ideas.md` — backlog идей для будущих запросов и route-ов;
- временные V1/V3 prompt drafts, если человек явно просит;
- planning notes, если они не выдают себя за live execution evidence.

`ork_planner_plan_full.md` является главным результатом текущей задачи. Он должен быть достаточно подробным, чтобы будущий Orc мог работать без угадывания, но он не является journal/status/active plan.

### 7.2. Orc-owned artifacts

Orc-owned layer появляется после явного запуска Orc execution phase. Сюда относятся:

- `ork_planner_plan_navigation.md`;
- `ork_planner_plan_index.md`;
- `ork_planner_readme.md`;
- `ork_planner_navigation.md`;
- `ork_planner_plan_active_N.md`;
- `ork_planner_journal.md`;
- `ork_planner_status.md`;
- `ork_planner_decisions.md` как live execution record;
- reports, review-resolution notes, testing/evidence tracking, если они понадобятся.

Важно: Orc-owned не означает, что Orc может делать всё сразу. Даже Orc должен работать slice-by-slice, через gates, с report и human checkpoints.

### 7.3. Почему нельзя заранее создать Orc-owned layer

Если Planner заранее создаёт `journal`, `status`, `active plan`, возникает ложное ощущение, что execution уже начался и что у подпроекта есть live state. Это опасно по двум причинам:

1. будущий Orc может принять placeholder-ы за факт;
2. человек может подумать, что система уже доказана, хотя был создан только черновик.

Поэтому текущий пакет содержит только один project file: `ork_planner_plan_full.md`.

<a id="canonical-artifact-model-for-this-pilot"></a>
## 8. Canonical artifact model for this pilot

Каноническая модель артефактов для `ork_planner` должна быть поэтапной. Не все документы появляются в один момент.

### 8.1. Stage 0 — External first draft package

Текущий stage.

Создаётся ZIP artifact package с одним project file:

```text
files/.ai/subprojects/ork_planner/ork_planner_plan_full.md
```

Служебные файлы package:

```text
manifest.yaml
README_FOR_KILO.md
README_FOR_CODEX.md
checksums.sha256
```

Эти служебные файлы не являются project files. Они нужны только для передачи и проверки artifact package.

Запрещено создавать в `files/` любые другие project files.

### 8.2. Stage 1 — Local Planner review

Planner и человек локально читают `ork_planner_plan_full.md` и решают:

- принять как основу;
- принять с правками;
- вернуть на доработку;
- отложить;
- заменить новым draft.

На этом этапе Orc всё ещё не запущен. Review может привести к ручным правкам или дополнительному external critique, но не должен автоматически создавать live operational layer.

### 8.3. Stage 2 — First Orc nav pass

После явного approval Orc получает ограниченную задачу:

- прочитать accepted `ork_planner_plan_full.md`;
- проверить anchors и quick navigation;
- поправить anchors в самом `plan_full`, если нужно;
- создать `ork_planner_plan_navigation.md`;
- создать тонкий `ork_planner_plan_index.md`;
- создать `ork_planner_readme.md`;
- остановиться;
- вернуть report.

На этом этапе ещё не создаётся общий `ork_planner_navigation.md`, не создаётся full live execution layer, не начинается repo-level alignment.

### 8.4. Stage 3 — Battle-plan creation

Отдельный шаг после nav pass. Orc подготавливает battle plans — не как красивую карту, а как конкретное руководство к исполнению большого `plan_full`.

Battle plans должны ответить:

- какие execution slices будут;
- какой порядок безопасен;
- где нужны Kilo runs;
- где нужны V1/V3 critique или waiver;
- какие files allowed/forbidden на каждом slice;
- какие human checkpoints нужны;
- какие gates закрываются после каждого slice;
- что делать при blocker.

Battle plans не запускают execution сами. После них нужен human approval.

### 8.5. Stage 4 — First docs execution slice

Только после approval battle plans Orc начинает первый реальный docs execution slice. По принятым planner decisions стартовый scope должен оставаться local-first и жить внутри `.ai/subprojects/ork_planner/`.

```text
.ai/subprojects/ork_planner/
```

Это значит:

- сначала создаётся и проверяется локальный doc-set самого `ork_planner`;
- repo-level файлы не входят в первый execution slice автоматически;
- `.ai/rules/*`, `.ai/repo_navigation.md` и `AGENTS.md` относятся к отдельной repo-level alignment wave после local proof.

Точный route и конкретные операции определяет Orc в рамках accepted battle plans.

### 8.6. Stage 5 — Local proof

Пилот считается доказанным не по факту создания файлов, а по evidence:

- Planner не вышел за роль;
- Orc стартовал только после approval;
- первый nav pass был ограниченным;
- battle plans были отдельным шагом;
- первый execution slice был выполнен по gates;
- journal/status/decisions появились только как Orc-owned live layer;
- человек смог понять состояние процесса;
- нет возврата к legacy route;
- repo-level alignment не начался раньше времени.

### 8.7. Stage 6 — Repo-level alignment wave

Только после local proof можно аккуратно выравнивать repo-level workflow docs. Это отдельная wave, не часть текущего first draft.

<a id="lifecycle-overview-from-planning-to-first-orc-run"></a>
## 9. Lifecycle overview from planning to first Orc run

Ниже описан полный lifecycle от текущего внешнего черновика до первого Orc run.

### 9.1. Шаг 1 — External V3 draft created

Внешний V3 artifact-producing workflow создаёт ZIP. Это текущая задача. Результат — не repo edit, а переносимый пакет.

Состояние после шага:

```text
Artifact exists outside repo workspace.
Repo unchanged.
No import.
No journaling.
No Orc.
```

### 9.2. Шаг 2 — Human downloads package

Человек скачивает ZIP. Это manual transfer step. Сам факт скачивания не является import и не является acceptance.

### 9.3. Шаг 3 — Local review route selected

Человек и Planner выбирают, как локально смотреть пакет. Варианты:

- просто открыть markdown и прочитать;
- распаковать в temporary holding area;
- запустить отдельный review через Kilo, если нужна локальная проверка package structure;
- позже, если человек явно попросит, пройти `/v3 import-entry` route.

Важно: текущий request прямо говорит, что import-stage не входит в задачу. Значит этот документ не должен требовать немедленного `/v3`.

### 9.4. Шаг 4 — Planner review

Planner проверяет:

- документ написан на русском;
- skeleton соблюдён;
- роль Planner удержана;
- Orc не запущен;
- исторический scaffold не скопирован как template;
- `Unresolved Decisions`, `Acceptance Gates`, `Anchor Map` есть;
- `Planner -> Orc` единственный active route;
- V3-first-draft не смешан с `/v3 import-entry`;
- future docs описаны, но не созданы.

### 9.5. Шаг 5 — Human acceptance or correction

Человек принимает решение. Возможные verdicts:

- `Accepted for local use`;
- `Accepted with edits`;
- `Needs revision`;
- `Rejected`;
- `Hold`.

Только после acceptance можно переходить к подготовке первого Orc step.

### 9.6. Шаг 6 — Orc activation is explicit

Orc активируется не потому, что существует `plan_full`, а потому что человек явно переводит работу в execution:

```text
План принят. Запускаем Orc на первый nav pass.
```

Или аналогичной фразой. Если такого перехода нет, Orc не стартует.

### 9.7. Шаг 7 — First Orc nav pass

Первый Orc run узкий. Он не делает всё. Его задача — сделать большой план читаемым и пригодным для будущей работы.

### 9.8. Шаг 8 — Stop and report

После nav pass Orc останавливается и возвращает report. Это gate. Нельзя сразу переходить к battle plans без review результата nav pass.

<a id="v3-v1-kilo-usage-and-recommend-or-waive-rule"></a>
## 10. V3 / V1 / Kilo usage and recommend or waive rule

V1/V3/Kilo — инструменты. Они не являются самостоятельными управляющими ролями. В `ork_planner` их выбор должен быть явным и объяснённым.

### 10.1. V3-Ревью

`V3-Ревью` уместен, когда нужен сильный внешний черновик важного документа или artifact package. Текущая задача именно такая: большой workflow document, где внешняя модель может дать широкий first draft, а Planner потом проверяет и принимает.

Но `V3-Ревью` не равно `/v3 import-entry`. Разница:

| Route | Смысл |
|---|---|
| `V3-Ревью` | tool-selection label: внешний artifact/draft создаётся для дальнейшего review |
| `/v3 import-entry` | shortcut route: человек уже имеет V3 package source и хочет импорт через Kilo Notebook V3 |

Для текущей задачи `/v3 import-entry` waived, потому что request прямо говорит: import-stage не часть задачи.

### 10.2. V1-Синтез

`V1-Синтез` может быть полезен позже для bounded second opinion. Например, после принятия `plan_full` можно отдельно спросить внешний чат:

- достаточно ли жёстко описаны three hard phases;
- не слишком ли слабый battle-plan gate;
- где возможен Planner/Orc role leak;
- достаточно ли отделён local proof от repo-level alignment.

Но V1 не должен использоваться как repo authority. Любой V1 ответ — input для review, а не факт о локальном repo.

### 10.3. Kilo

Kilo нужен, когда требуется локальная repo-grounded работа:

- проверить файлы;
- изменить файлы;
- увидеть diff;
- запустить проверки;
- импортировать package через настроенный route;
- создать report.

Первый Orc nav pass заранее планируется как Kilo route, но конкретный Kilo mode будущий Orc должен выбрать после чтения принятого `plan_full`. Это важно: Planner фиксирует цель и boundaries, но не обязан заранее жёстко выбирать runtime детали, если planner decision прямо оставляет это Orc-у.

### 10.4. Recommend or waive rule

Для каждого крупного будущего шага Orc должен явно указать:

```text
Subagent Tool: <V1-Синтез | V3-Ревью | Kilo | Субагент-микро | waived>
Reason: <почему выбран или почему waived>
```

Если инструмент не нужен, это нужно писать как `waived`, а не молча пропускать. Пример:

```text
Subagent Tool: waived
Reason: docs-only review by human; no local file edit or external critique needed at this gate.
```

Так будущий reader поймёт, что инструмент не забыли, а сознательно не использовали.

<a id="first-v3-first-draft-route-and-why-it-is-not-v3-import-entry"></a>
## 11. First V3-first-draft route and why it is not /v3 import-entry

Текущий пакет — это first draft generation route. Он создаёт внешний artifact, но не запускает import lane.

### 11.1. Что происходит сейчас

Сейчас создаётся ZIP:

```text
V3-20260601-011520-ork-planner-plan-full-first-draft/
  manifest.yaml
  README_FOR_KILO.md
  README_FOR_CODEX.md
  checksums.sha256
  files/.ai/subprojects/ork_planner/ork_planner_plan_full.md
```

Внутри `files/` ровно один project file. Это важно для safety: package не может скрыто притащить соседние документы.

### 11.2. Что не происходило на стадии external generation

На стадии external V3 package generation не происходило:

- `/v3` shortcut;
- Kilo Notebook V3 launch;
- import;
- validation через локальные scripts;
- journaling;
- запись в `.ai/v3/`;
- запись в `.ai/subprojects/ork_planner/`;
- обновление navigation;
- acceptance.

### 11.3. Почему это безопасно

Такой route был безопасен, потому что он создавал сильный черновик без изменения repo. Planner мог проверить содержание до того, как файл попадёт в workspace. Это особенно важно для workflow-документа, который может повлиять на роли и процесс.

Теперь файл уже импортирован в repo для локального review, но distinction остаётся важным: external draft generation и local acceptance — разные стадии.

### 11.4. Когда `/v3 import-entry` станет уместен

`/v3 import-entry` станет уместен только если человек позже скажет примерно:

```text
У меня есть V3 package. Подготовь import через Kilo Notebook V3.
```

Тогда Codex должен использовать соответствующий `/v3` шаблон и route. Но это отдельная задача, не текущий package generation.

<a id="first-orc-nav-pass"></a>
## 12. First Orc nav pass

Первый Orc nav pass — первый реальный execution шаг после принятия `plan_full`. Он намеренно узкий.

### 12.1. Цель nav pass

Цель — сделать большой план пригодным для работы:

- проверить, что anchors есть и стабильны;
- проверить, что Quick Navigation ведёт на правильные разделы;
- создать отдельный маршрут чтения большого плана;
- создать тонкий index по anchors;
- создать readme для входа человека в подпроект;
- не начать execution по содержанию плана.

### 12.2. Разрешённый scope первого nav pass

Первый nav pass может touching только:

```text
.ai/subprojects/ork_planner/ork_planner_plan_full.md
.ai/subprojects/ork_planner/ork_planner_plan_navigation.md
.ai/subprojects/ork_planner/ork_planner_plan_index.md
.ai/subprojects/ork_planner/ork_planner_readme.md
```

При этом `plan_full` можно менять только для navigation/anchor quality: anchors, quick links, typo-level fixes, possibly short clarifying navigation note. Нельзя переписывать стратегию без отдельного Planner review.

### 12.3. Forbidden in first nav pass

Первый nav pass не должен создавать:

```text
.ai/subprojects/ork_planner/ork_planner_navigation.md
.ai/subprojects/ork_planner/ork_planner_plan_active_1.md
.ai/subprojects/ork_planner/ork_planner_journal.md
.ai/subprojects/ork_planner/ork_planner_status.md
.ai/subprojects/ork_planner/ork_planner_decisions.md
```

Он также не должен менять:

```text
.ai/rules/
.ai/repo_navigation.md
.ai/project_state.md
AGENTS.md
ideas/
.ai/v3/
```

### 12.4. Expected report after nav pass

После nav pass Orc должен вернуть report с минимумом:

- что прочитано;
- какие файлы созданы;
- какие изменения внесены в `plan_full`;
- какие files intentionally not touched;
- checksum/diff summary, если доступно;
- `Human Check` простым русским языком;
- `Баги и сложности`;
- open blockers, если есть;
- next recommended step: battle-plan creation, not execution.

<a id="battle-plan-creation-and-approval-gate"></a>
## 13. Battle-plan creation and approval gate

Battle plans — это мост между большим стратегическим `plan_full` и реальными execution slices.

### 13.1. Почему battle plans нужны отдельно

Большой `plan_full` объясняет систему. Он широк. Но Orc-у для выполнения нужны конкретные боевые шаги:

- что делать первым;
- какие файлы можно менять;
- где остановиться;
- какие checks нужны;
- какие human approvals нужны;
- как откатываться при blocker.

Если сразу перейти от `plan_full` к live execution, Orc может начать выбирать слишком большой scope. Battle plans уменьшают этот риск.

### 13.2. Battle-plan creation как отдельный Kilo run

Planner decisions фиксируют: nav pass и battle-plan creation — разные Kilo runs. Это дисциплина безопасности.

Run 1:

```text
First Orc nav pass
```

Run 2:

```text
Battle-plan creation
```

Только после Run 2 и human approval можно начинать Run 3 / первый реальный docs execution slice.

### 13.3. Что должен содержать battle plan

Каждый battle plan должен содержать:

- `Plan ID`;
- цель slice;
- source basis;
- allowed paths;
- forbidden paths;
- exact task boundaries;
- selected tool or waived tool;
- Kilo mode recommendation, если нужен Kilo;
- expected outputs;
- verification steps;
- planned human checkpoints;
- rollback/blocker behavior;
- acceptance criteria;
- explicit stop condition.

### 13.4. Approval gate

После battle-plan creation нельзя автоматически начинать execution. Нужен gate:

```text
Human approval required before first docs execution slice.
```

Human approval должен быть понятен, например:

```text
Принято. Запускаем первый execution slice по battle plan 1.
```

Если человек говорит «в целом нормально» без явного запуска, Orc должен уточнить или вернуть pending status, а не начинать repo changes.

<a id="three-hard-phases-of-the-pilot"></a>
## 14. Three hard phases of the pilot

Пилот `ork_planner` должен идти через три жёсткие фазы. Эти фазы нельзя смешивать.

### 14.1. Phase 1 — Planner proof

Цель Phase 1: доказать, что Planner умеет создать стратегический document и не перейти в execution.

Phase 1 включает:

- external first draft package;
- local Planner review;
- human acceptance или revision;
- фиксацию, что Orc ещё не запущен;
- сохранение одного active route `Planner -> Orc`;
- отказ от создания соседних live docs до Orc phase.

Phase 1 успешно завершена, если:

- `plan_full` принят как planning basis;
- open decisions честно перечислены;
- acceptance gates определены;
- future Orc work описана, но не исполнена;
- user понимает следующий шаг.

### 14.2. Phase 2 — Orc bootstrap proof

Цель Phase 2: доказать, что Orc может стартовать ограниченно и не раздувать execution.

Phase 2 включает:

- explicit Orc activation by human;
- first nav pass;
- creation of `plan_navigation`, `plan_index`, `readme`;
- stop and report;
- no full live execution layer yet;
- separate battle-plan creation;
- human approval gate.

Phase 2 успешна, если:

- Orc не вышел за nav scope;
- navigation docs помогают читать план;
- battle plans готовы отдельно;
- человек видит, что execution ещё не начался по содержанию;
- gate перед execution не пропущен.

### 14.3. Phase 3 — Local execution proof before repo alignment

Цель Phase 3: доказать, что первый реальный docs execution slice проходит по новой модели.

Phase 3 включает:

- первый docs execution slice после approval;
- создание минимального live execution layer только тогда, когда он действительно нужен;
- updates в scope первого внедрения;
- journal/status/decisions как Orc-owned live record;
- human checkpoints;
- verification report;
- final local proof verdict.

Phase 3 успешна, если:

- Orc выполняет accepted plan, а не переписывает его молча;
- evidence достаточен;
- человек может восстановить состояние по документации;
- нет hidden execution;
- нет преждевременной repo-level wave;
- blockers либо закрыты, либо честно вынесены.

<a id="local-proof-and-human-acceptance-model"></a>
## 15. Local proof and human acceptance model

Acceptance пилота нельзя считать по количеству файлов. Файлы можно создать и при сломанном процессе. Доказательство должно быть поведенческим.

### 15.1. Что такое local proof

Local proof — это evidence, что модель работает в пределах `ork_planner`.

Минимальный local proof:

1. Planner создал/принял `plan_full`, не запустив execution.
2. Orc был запущен явно.
3. Первый Orc nav pass был узким.
4. Battle plans были отдельным step.
5. Первый execution slice начался только после human approval.
6. Orc поддерживал live evidence.
7. Human check был понятен не-программисту.
8. При blocker система не замолчала, а вернулась в clarification/planning.

### 15.2. Human acceptance language

Документы должны использовать простые human-facing формулировки. Например:

```text
Human Check: suggested
Открой `ork_planner_plan_navigation.md` и проверь, понятно ли, в каком порядке читать большой план. Если ссылки ведут не туда или разделы называются непонятно, верни сообщение: "navigation не принята" и коротко скажи, что сбивает.
```

Не подходит:

```text
Validate semantic navigation layer according to anchor topology.
```

Пользователь не обязан быть программистом. Документы могут содержать technical identifiers, но инструкции человеку должны быть простыми.

### 15.3. Verdicts

Рекомендуемые verdicts:

- `Accepted` — gate закрыт полностью;
- `Partially accepted` — часть результата годится, часть требует follow-up;
- `Blocked` — нельзя идти дальше;
- `Needs revision` — нужен новый pass;
- `Rejected` — результат не подходит;
- `Held` — решение отложено.

`Accepted` нельзя ставить без evidence. `Partially accepted` должен ясно говорить, что можно использовать, а что нельзя.

<a id="repo-level-alignment-wave-after-local-proof"></a>
## 16. Repo-level alignment wave after local proof

Repo-level alignment wave — это обновление стабильного workflow layer после того, как пилот доказал модель локально. Она не является частью текущего first draft и не должна начинаться до Phase 3 proof.

### 16.1. Почему alignment позже

Если сразу менять repo-level правила, можно закрепить ошибку. Например:

- Planner/Orc граница окажется слишком слабой;
- nav pass окажется слишком широким;
- battle plans будут неудобны;
- session/journal separation окажется непонятной;
- human checkpoints будут слишком техническими.

Локальный пилот позволяет увидеть это на малом scope.

### 16.2. Минимальный будущий repo-level scope

Planner decisions указывают минимальный будущий scope первого внедрения:

```text
.ai/rules/codex_role_planner.md
.ai/rules/codex_role_orc.md
.ai/rules/codex_orchestrator.md
.ai/repo_navigation.md
AGENTS.md
```

`project_state` сейчас не обязателен в первом docs-slice. Это важно: не надо расширять scope без необходимости.

### 16.3. Alignment gate

Перед repo-level alignment должны быть закрыты gates:

- `plan_full` accepted;
- nav pass accepted;
- battle plans approved;
- first execution slice accepted;
- local proof report accepted;
- unresolved decisions reviewed;
- human understands next wave.

Если хотя бы один gate открыт, alignment wave должна быть blocked или held.

<a id="session-binding-and-session-journal"></a>
## 17. Session binding and session != journal

Session и journal решают разные задачи. Их нельзя смешивать.

### 17.1. Session

Session — это рабочий контекст конкретного чата/запуска. Он отвечает на вопросы:

- какой у нас текущий goal;
- какой approved plan;
- какой active plan item;
- какие runs были;
- какие user overrides были;
- какой checkpoint state.

Session может жить в `.ai/plans/sessions/...` или другом session layer в зависимости от repo rules. Он шире одного подпроекта и связан с orchestration flow.

### 17.2. Journal

Journal подпроекта — это Orc-owned live execution record внутри `.ai/subprojects/ork_planner/`. Он отвечает на вопросы:

- что фактически было сделано в подпроекте;
- когда был выполнен step;
- каким tool route;
- какой report/evidence;
- какой human verdict;
- какие blockers появились;
- что стало следующим шагом.

### 17.3. Почему session != journal

Если session заменить journal-ом, подпроект потеряет локальную историю execution. Если journal заменить session-ом, repo-level orchestration потеряет контроль над текущим чатом и Kilo runs.

Правило:

```text
Session binds the current orchestration conversation.
Journal records factual subproject execution history.
```

Для текущей задачи journal не создаётся, потому что Orc ещё не запущен и repo не меняется.

### 17.4. Когда journal появится

<a id="unresolved-decisions"></a>
## 20. Unresolved Decisions

Эти решения намеренно не закрываются в first draft. Они должны быть рассмотрены Planner-ом/человеком или будущим Orc-ом в нужной фазе.

### UD-001 — Какой repeatable route применять к будущим V3 ZIP artifact-ам

Варианты:

- manual extraction в repo после local review;
- local holding area;
- `/v3 import-entry` позже;
- Kilo verification package;
- прямой manual application.

Для текущего first draft локальный route уже выбран: manual extraction после local review ZIP. Но общий repeatable policy для будущих похожих V3 packages ещё не зафиксирован.

### UD-002 — Нужно ли делать отдельный V1 critique после принятия first draft

Идея уже есть в planner request ideas. Полезно проверить battle-plan structure и gates внешним bounded second opinion. Но это не обязательно для текущего package.

### UD-003 — Точный Kilo mode для первого nav pass

Planner decisions фиксируют, что первый nav pass идёт через Kilo, но конкретный mode оставлен будущему Orc. Это правильно: Orc должен выбрать route после чтения принятого `plan_full` и актуального локального состояния.

### UD-004 — Формат battle plans

Этот документ задаёт минимальные блоки, но не утверждает окончательный template. Первый battle-plan creation step должен предложить конкретный формат и получить approval.

### UD-005 — Сколько `plan_active_N` нужно в первой execution wave

Первый active plan может быть один, но если scope разделится на несколько безопасных slices, может понадобиться `plan_active_2`, `plan_active_3`. Это решается после battle plans.

### UD-006 — Когда именно создавать `ork_planner_navigation.md`

Planner decisions говорят: не в первом nav pass, а позже. Точный момент — после nav pass, battle plans и approval. Будущий Orc должен выбрать конкретный slice.

### UD-007 — Нужен ли отдельный reports file

`reports` может быть полезен, но не должен появляться автоматически. Решение зависит от количества execution evidence и удобства чтения.

### UD-008 — Какой минимум repo-level alignment считать достаточным

Предварительный минимум известен, но после local proof может выясниться, что нужна дополнительная правка language policy, session docs или prompts. Это нельзя решать сейчас без evidence.

### UD-009 — Как фиксировать review-resolution после внешних critique

Нужно решить, где жить review notes: в отдельной reviews area, в decisions, в journal или в report. До живого Orc layer это не закрывается.

### UD-010 — Нужна ли отдельная проверка на русский язык для user-facing docs

Так как пользователь явно требует русский документ, будущие gates могут включать language check: user-facing explanations in Russian, identifiers in English. Решить нужно до массового repo-level alignment.

Acceptance gates — это контрольные ворота. Их нельзя закрывать по настроению. Нужен evidence или явный human verdict.

- есть `manifest.yaml`;
- есть `README_FOR_KILO.md`;
- есть `README_FOR_CODEX.md`;
- есть `checksums.sha256`;
- `files/` содержит ровно один project file;
- project file path exactly `.ai/subprojects/ork_planner/ork_planner_plan_full.md`;
- checksums match.

Owner: external artifact generator.  
Status for imported source ZIP: locally checked before import.

Owner: external artifact generator + Planner review.
